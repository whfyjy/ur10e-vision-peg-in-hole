## 零、先把期望对齐

### 这个项目在面试里值多少

它**不是**一篇论文级的工作，不要包装成那样。它的真实价值在三处：

| 你有的 | 大多数人没有的 |
|---|---|
| 一个**端到端跑通**的机器人视觉 RL 环境（Isaac Lab + rsl_rl，不是 gym 玩具） | 大部分简历上的 RL 项目是 CartPole、Atari，没有物理接触、没有真实几何 |
| 一份**诚实的实验记录**：哪里失败了、怎么定位的、哪些结论被自己推翻过 | 大多数人只写"最终成功率 X%"，没有失败分析 |
| **几个真正难的工程判断**：0.6 mm 间隙为什么必须"先对准再缓降"、为什么不能用框架自带的图像归一化、为什么最后那个检查点是废的 | 这些细节只有真跑过才知道，背不出来 |

**面试官不会考你会不会写 PPO**（那是笔试的事）。他们会问"为什么这么设计"、"出问题你怎么查"——而这两个问题正好是这个项目攒下来的东西。

### 时间预期（诚实版）

按每天 2–3 小时算：

| 阶段 | 内容 | 时长 |
|---|---|---|
| 0 | 跑起来、看懂数据 | 2–3 天 |
| 1 | MDP：这个任务到底是什么 | 5–7 天 |
| 2 | PPO：它到底在调什么 | 7–10 天 |
| 3 | 视觉与 CNN | 5–7 天 |
| 4 | 实验设计与调试 | 5–7 天 |
| 5 | 工程细节（场景、相机、USD） | 5–7 天 |
| | **合计** | **约 1 个月** |

"掌握"不是"读完代码"。**读完只要三天，讲不出来等于没学。**

### 三档标准（自己测）

- **第一档（能写进简历）**：能跑通所有脚本，能解释 `success %` 是什么意思、`parse` 为什么从 2.6 涨到 10。→ 约 3 天。
- **第二档（能扛面试）**：能画出数据流图（图像 → 网络 → 关节目标 → 物理 → 奖励 → 更新），
  能解释每个超参数为什么是这个值，能讲清楚"训练失败时你怎么办"。→ 约 2 周。
- **第三档（能独立做新任务）**：换个机械臂 / 换个任务，你能从零搭出环境并训出来。→ 约 1 个月，且需要真的动手改。

简历写第一档的话就够了，但**面试只能过第二档的关**。

## 第 1 阶段：MDP——这个任务到底是什么（5–7 天）★ 最该先啃

## 第 2 阶段：PPO——它到底在调什么（7–10 天）★ 面试重点

到这里你必须**直接读库源码**了。二手教程（博客、视频）会把 PPO 讲成"三个 loss 加起来"，
但面试官一问细节就露馅。好消息是 rsl_rl 的 PPO 实现很干净，一共 476 行。

源码位置（确认过）：

```
RSL=/home/whf/whf/miniconda3/envs/isaac_env/lib/python3.10/site-packages/rsl_rl
```

### 目标

能自己写出 PPO 的目标函数，能解释每个超参数在控制什么，能看懂训练日志里每个数字的来源。

### 读

**1. `$RSL/modules/actor_critic.py`（149 行）—— 先读这个，最短**

这是网络本体。看清楚：

- `act()` 采样动作，`act_inference()` 用均值（确定性）—— **这就是 `eval.py` 里
  `--action sampled` 和 `--action deterministic` 的区别来源**。
- `evaluate()` 算 value，`update_distribution()` 用新参数重算旧动作的对数概率——PPO 的核心机制。
- `std` 是一个**可学习的参数**（不是超参）。这就是为什么它会跑飞（见下）。

**2. `$RSL/storage/rollout_storage.py`（316 行）—— 读 `compute_returns()`**

GAE（广义优势估计）。搞清楚 `gamma`（0.99）和 `lam`（0.95）分别在做什么：

- `gamma` 是"未来的奖励打几折"
- `lam` 是"优势估计里偏差和方差的权衡"
- 这两个值在本项目里是 genpih 传下来的，没改过

**3. `$RSL/algorithms/ppo.py`（476 行）—— 主角，读三遍**

第一遍通读，搞清楚主循环结构。第二遍只看 `update()` 里这三个 loss：

```python
surrogate_loss      # 策略损失：让好动作概率变大，但 clip_param=0.2 限制每步别变太多
value_function_loss # 价值损失：让 critic 预测得准
entropy             # 熵：鼓励探索。本项目 entropy_coef=0.0 —— 关掉了
```

第三遍带着这个问题读：**`use_clipped_value_loss=True` 和 `clip_param=0.2` 分别在 clip 什么？**

**4. `$RSL/runners/on_policy_runner.py`（539 行）—— 读 `learn()`**

这是训练主循环：收集 rollout → 更新 → 记录日志 → 存检查点。
重点看两处：

- 日志是怎么算的（`ep_infos` 那一堆），因为这决定了你 tensorboard 上看到的数字的含义
- 第 71 行附近的 `eval(self.policy_cfg.pop("class_name"))`——
  **这一行是本项目能注入自定义 CNN 的关键**（第 3 阶段详讲）

**5. `pegih_tasks/config/rsl_rl_ppo_cfg.py`（105 行）—— 全是注释，注释就是文档**

这个文件的注释比代码多，**每一段注释都是一次失败的记录**。特别是：

- `noise_std_type` 那段：我一度以为改这里能修 bug，后来被实验推翻
- `learning_rate` 那段：那张检查点扫描表说明了 1e-3 能训出好策略但**守不住**
- `schedule` 那段：为什么不能用 rsl_rl 默认的 `"adaptive"`

### 做

**练习 2.1 — 数一遍一次迭代发生了多少事**

跑 1 次迭代（`--max_iterations 1`），在 `$RSL/algorithms/ppo.py` 的 `update()` 里
临时加 `print`，数出来：

- 一次 `learn()` 里 `update()` 被调几次？（提示：`num_learning_epochs=5`, `num_mini_batches=4`）
- 每次 `update()` 里网络的 `backward()` 被调几次？
- 所以**一次 rollout 的数据被用了几遍**？这个数字和 PPO 的样本效率有什么关系？

**练习 2.2 — 亲手制造一次 critic 发散**

这是本项目最真实的 bug。做法：把 `learning_rate` 从 `1e-3` 改成 `1e-2`，
跑一次短训练，观察 `Loss/value_function`：

```bash
$PY scripts/train.py --headless --num_envs 256 --max_iterations 150 --run_name test_diverge
tensorboard --logdir runs/rsl_rl/pegih_vision
```

看 `Loss/value_function` 是不是指数放大（README 记的真实数据是 `4.3 → 91 → 1.3e7`）。

**然后回答**：为什么 `max_grad_norm=1.0`（梯度裁剪）没能挡住它？
（提示：梯度裁剪只限制**梯度大小**，挡不住**目标值本身的爆炸**。目标值是
`reward + gamma * V(s')`，如果 `V` 已经很大，目标值就更大，正反馈。）

做完这个练习，你就理解了 `pegih_tasks/train_guard.py`（142 行）为什么存在。
**把它读一遍**：它做的事很简单——每步记一下 value loss，如果连续 2 次超过基线的 1000 倍就
存盘并抛异常终止训练，免得后面所有检查点都被毁掉。

**练习 2.3 — 重新推导 KKT... 不，是重新推导 PPO 的 clip**

拿纸笔，写出 PPO 的策略损失：

```
L = min( r * A,  clip(r, 1-ε, 1+ε) * A )
```

其中 `r = π_new(a|s) / π_old(a|s)`。分四种情况（A>0/A<0 × r 越界/未越界）
讨论这个 min 在干什么。**能讲清楚"为什么要 min"，PPO 就过关了。**

## 第 3 阶段：视觉与 CNN（5–7 天）

这个项目的卖点是"纯视觉"，所以这部分必须讲得比 PPO 还熟。

### 目标

理解从"相机拍到一张图"到"网络输出 6 个关节目标"的完整链路，以及中间两个非平凡的工程决定。

### 读

**1. `pegih_tasks/tasks/peg_hole/cnn_policy.py`（196 行）—— 全读**

rsl_rl 2.3.3 **不自带 CNN**，所以这个文件是手写的。三个关键点：

- **`ImageEncoder.forward` 里的 `view(N,h,w,c).permute(0,3,1,2)`**：
  为什么要这么绕？因为图像在 `mdp.camera_image` 里被**展平成一行**了（30000 维），
  网络必须把它**还原回 100×100×3** 才能做卷积。为什么展平？见下一条。
- **`ActorCriticCNN.__init__` 直接调 `nn.Module.__init__(self)`**（不是 `super().__init__()`）：
  因为父类 `ActorCritic` 的 `__init__` 会先建一个 `Linear(30000, 256)` 的层，
  那层下一秒就被丢掉——30000×256 白白分配一次，浪费显存和时间。
- **`install()`**：把类绑进 `rsl_rl.runners.on_policy_runner` 的模块命名空间。
  因为那个 runner 用 `eval("ActorCriticCNN")` 按**字符串**解析类名，
  而 `eval` 只在**自己的模块 globals** 里找。所以要在别处把类塞进去。
  **这是个 hack，但注释里写清楚了为什么，面试时讲这个 hack 比讲网络结构更加分。**

**2. `peg_hole_env_cfg.py` 里的相机配置**

找到 `TiledCameraCfg` 那段，搞清楚每个参数：

- `prim_path="{ENV_REGEX_NS}/Robot/wrist_3_link/Camera"` —— 挂在**手腕**上（眼在手上）
- `update_period=1/60` —— 每个控制步渲染一次（控制频率 60 Hz）
- `focal_length=24.0` + `aperture=20.955` —— 决定了视场角 HFOV ≈ 47.2°
- `clipping_range=(0.05, 20.0)` —— 最近 5 cm，远 20 m

## 第 4 阶段：实验设计与调试（5–7 天）★ 最能拉开差距

**这一阶段是这个项目区别于"网上抄的 RL 项目"的地方。**
大部分人的项目是"跑通了、成功了、写进简历"，没有失败分析。你有一堆。

### 目标

建立**实验纪律**：什么时候能下结论、什么时候不能。

### 读

- README「同代码同 seed，三次重训只有一次学会」一整节
- README「已知问题」一整节
- `best_policy/README.md`
- `docs/训练手册.md` 的「怎么判断它在学」「选检查点」「监控与排错」三节

### 核心概念（这几条要能背下来）

**1. 重训失败 ≠ 代码回归**

三轮**完全相同的代码、超参、seed 42**，只有一轮学会。为什么 seed 没钉住？
因为 Isaac 的场景和渲染器构建会消耗随机流——同一份代码在不同时刻跑，随机数序列不同。

**教训**：看到"改了 X 之后训练失败"，不要立刻怪 X。
**先用一个冻结的、已知能用的检查点回放**：

```bash
$PY scripts/eval.py --headless --checkpoint best_policy/model_550.pt --num_envs 32 --episodes 3
```

如果回放还是 100%，说明环境没坏，问题在训练。这一步能把排查范围砍掉一半。
（README 记：当时已经核对了五六个文件，靠这一步才把方向扭回来。）

**2. 永远不要用最后一个检查点**

两组训练都是这样：

| | 最优检查点 | 最后一个检查点 |
|---|---|---|
| 视觉 | `model_550` → 100% | `model_799` → return **0.20** |
| 状态 | `model_3875` → 100% | `model_5150` → return **0.45**，已在崩溃边缘 |

崩溃的原因是 critic 发散（第 2 阶段练习 2.2 你亲手制造过）。
`model_600` 之后全部归零：`Loss/value_function` 从 4.3 → 91 → 1.3e7。

**所以必须做检查点扫描**，用 `eval.py --scan_stride` 或 `--which best`。

**3. 平台期是假象**

状态组在第 988 次迭代稳在 `parse=2.5`（看起来完全像收敛到局部最优），
第 **1482** 次才突破，最终到 9.84。

**教训**：预算给不够时，"学不会"和"还没到时候"长得一模一样。不要过早下结论。

### 做

**练习 4.1 — 复现检查点扫描**

```bash
$PY scripts/eval.py --headless --run_dir runs/rsl_rl/pegih_vision/2026-10-08_22-56-56_vision \
    --scan_stride 50 --scan_episodes 1 --num_envs 32
```

自己画出那条生死曲线，和 `best_policy/README.md` 里的对照。**看 model_400 那个凹陷**——
那是短暂塌陷后自行恢复，和 model_600 的彻底死亡是两回事。**区分这两者是这个项目的关键技能。**

**练习 4.2 — 设计一个实验（最重要）**

提出一个假设，设计实验去证伪它。例如：

> **假设**：把 `learning_rate` 降到 `3e-4`，就不会再出现 model_600 那种崩溃。

设计这个实验时你必须回答：

- 跑几次才够？（提示：三次里只有一次学会，所以**跑一次说明不了任何事**）
- 怎么判断"没崩溃"是学习率的作用，而不是运气？（提示：看 `Loss/value_function` 的峰值，
  这个量比成功率稳定得多，可以跨 run 比较）
- 如果预算只够跑两次，你能得出什么结论？（提示：什么都得不出。要诚实承认。）

**这个练习的目的不是真的跑出结果，是让你体会"样本量不够时不要下结论"。**
面试官问"你怎么知道是 A 不是 B"，能答上这个的人不多。

**练习 4.3 — 读一遍 guard，想清楚它为什么是必要的**

`pegih_tasks/train_guard.py`（142 行）。它的逻辑是：value loss 超过基线的 1000 倍
且持续 2 次，就存盘 + 抛异常。

**想清楚**：为什么是"存盘**再**抛异常"，而不是直接抛？
（提示：rsl_rl 是**先记日志、再存检查点**，如果直接抛异常，最新那个检查点就丢了。
guard 的 `log()` 里有一行注释专门说这个。）

### 验收

1. 别人告诉你"我改了学习率之后训练变好了"，你怎么判断他说得对不对？
2. `parse` 卡在 2.6 有几种可能？分别怎么区分？
3. 为什么 `eval.py` 要同时报 **sampled** 和 **deterministic** 两种成功率？
