# 训练手册

面向自己手动跑训练的场景。所有命令里的 `PY` 都是：

```bash
PY=/home/whf/whf/miniconda3/envs/isaac_env/bin/python
cd "/home/whf/whf/ur10e-peg-in-hole rl"
```

> **路径含空格**，所有命令里的项目路径都要加引号。

> **已有的可用检查点**（评估已验证，详见 README 顶部表格）：
> - 视觉：`runs/rsl_rl/pegih_vision/2026-10-08_22-56-56_vision/model_550.pt` —— success **100%**（确定性）
> - 状态：`runs/rsl_rl/pegih_vision/2026-10-09_16-00-10_state_long_resume/model_3875.pt` —— success **100%**（两种动作源）
>
> 想在自己的训练里继续往上走，可以从这两个之一 `--resume` 续训，而不是从零开始。

## 一、最短路径

```bash
# 1) 先确认环境没坏（约 2 分钟）
$PY scripts/smoke_test.py --headless --no-vision

# 2) 短跑确认训练链路（约 1 分钟）
$PY scripts/train.py --headless --no-vision --num_envs 256 --max_iterations 20

# 3) 正式训练：状态观测（快，先拿到可靠结果）
$PY scripts/train.py --headless --no-vision --num_envs 1024 --max_iterations 12000 --run_name state2

# 4) 正式训练：视觉（慢，但这是本项目的目标）
$PY scripts/train.py --headless --num_envs 512 --max_iterations 3000 --run_name vision2
```

**建议顺序：先跑状态组。** 它一小时就能跑完 genpih 同等量级的预算，能干净地回答"这个任务
在我们的场景里到底收敛到什么程度"；视觉组要慢 20 倍，等状态组给了基准再做判断更省时间。

## 二、两种观测模式怎么选

| | 状态观测 `--no-vision` | 视觉（默认） |
|---|---|---|
| 策略输入 | 13 维（孔位姿在 peg 系 7 + 上一步动作 6） | 100×100×3 图像展平 30000 维 |
| critic 输入 | 14 维特权状态 | 同上（`--symmetric-critic` 可让 critic 也吃图像） |
| 速度（实测） | 1024 环境 **≈9.5 万 steps/s** | 512 环境 **≈5 千 steps/s** |
| 显存（实测） | 1024 环境 ≈5 GB | 512 环境 **21.7 GB**（1024 必 OOM） |
| 一小时能跑 | ≈3.4 亿步 | ≈1800 万步 |

**显存是硬约束**：视觉模式 512 环境已经占掉 21.7/24.5 GB，`--num_envs` 不能再往上加。
要更大批量只能降分辨率或改灰度（`mdp.camera_image` 里把 rgb 换成单通道）。

## 三、预算该给多少

参考 genpih 在同一任务上的对照：**3000 次迭代 × 8192 环境 ≈ 5.9 亿步**。

| 目标 | 状态组 | 视觉组 |
|---|---|---|
| 看学习信号通不通 | 400 轮 / 2000 万步 / **4 分钟** | 800 轮 / 2000 万步 / **1 小时** |
| 到达可用水平 | 4000 轮 / 2 亿步 / **35 分钟** | 需要 ≈5.9 亿步 ≈ **33 小时**（不现实） |
| genpih 同等预算 | 12000 轮 / 5.9 亿步 / **1.7 小时** | 同上，不可行 |

视觉组现实的打法是**跑几小时 + 靠选检查点拿最好的那个**，而不是追求跑够步数。

## 四、怎么判断它在学（以及最大的坑）

盯训练日志里的 **`Episode_Reward/parse`**：

- `2.6` = 全程只"对准"没插入
- `10` = 全程插着
- 中间值线性对应插入步数占比（`6.5` ≈ 53% 的步数插进去了）

### 坑：平台期是假象，不要过早下结论

实测：状态组在第 **988** 轮时稳稳停在 `2.5`（≈92% 步数对准、一次没插进去），
看起来完全像收敛到了局部最优。它**在第 1482 轮才突破**，一路涨到第 3881 轮的 **9.84**。

**给不够预算时，"学不会"和"还没到时候"看起来一模一样。** 至少给到 4000 轮再判断。

### 坑：塌陷是真的

实测：视觉组第 551 轮峰值 `8.28`，**末轮（799）`0.00`**——完全塌陷。
状态组在崩溃前也从 9.84 掉到 3.85。

**永远不要取最后一个检查点。** 见下一节。

## 五、选检查点（必做，不是保险）

genpih 的做法是扫描检查点、按指标选最好的，不是取最后一个。本环境实测确认了这条的必要性：
直接拿视觉组的 `model_799.pt` 会得到一个**什么都做不了**的策略，而它的 `model_550.pt` 有 78%。

`eval.py --which best` 会自动扫（按 `insert/step` 选）：

```bash
$PY scripts/eval.py --headless --which best \
    --run_dir runs/rsl_rl/pegih_vision/2026-10-09_XX-XX-XX_vision \
    --num_envs 32 --episodes 2
```

输出三行数字：

- **`success %`** —— 回合中至少成功插入过一次的比例（**论文口径**）
- **`insert/step`** —— 每步处于插入状态的环境比例（更灵敏，选点用它）
- **`return`** —— 平均回报

采样/确定性两种动作都会报。**部署看确定性那行**；训练日志和论文曲线对应采样那行。

默认每 25 轮存一个检查点（`save_interval`）。想更细就改
`pegih_tasks/config/rsl_rl_ppo_cfg.py` 里的 `save_interval`。

## 六、监控与排错

### 跑后台任务

**不要**把长任务接管道给 `tail`：

```bash
# 错误：tail 缓冲到 EOF 才输出，崩溃信息会被吞掉，而且管道退出码是 tail 的（永远 0）
python train.py ... | tail -20 &

# 正确：写文件，随时 tail 查看
nohup python scripts/train.py ... > /tmp/train.log 2>&1 &
tail -f /tmp/train.log
```

本会话有两次训练就是因为这个看起来"正常结束"，实际是崩溃。

### 崩溃：已有自动守卫，不用盯着

长跑基本都会以 **critic（价值网络）发散**结束——`Loss/value_function` 连续几步按 ×1e6 放大到 float32
上限，然后崩。**这时策略本身还是好的**（实测崩溃瞬间 `parse = 9.74`）。

`train.py` **默认开启了守卫**（`pegih_tasks/train_guard.py`）：检测到发散就**自动存检查点并停止**，
打印回滚指引。想关掉加 `--no-guard`。

判断规则是"当前 loss 超过**最近 5 轮的中位数**的 1000 倍，且连续 2 轮如此"。用中位数而不是上一轮的值，
是因为真实数据里有一种形态（视觉组就是）：

```
1.1  →  1e7  →  3e7
         ↑ 第一次跳了 9e6 倍     ↑ 第二次只跳 3 倍，但已经在发散中
```

跟"上一轮"比，第二次就不像跳变了；跟滚动中位数比才抓得住。它同时也忽略单次尖峰后回落的假警报。

**为什么要在"开始发散"时就停，而不是等它崩：** 发散在把 loss 炸掉之前，**已经先把策略弄坏了**：

```
model_5075   insert/step 0.9436
model_5150   insert/step 0.4521     ← 75 轮后已经被污染
（下一轮 loss 就到 1e25，崩溃）
```

等它崩，你手上最新的检查点就是坏的那个。收到守卫的提示后按它打印的步骤做：

```bash
# 1) 在崩溃点之前的检查点里扫，选最好的
$PY scripts/eval.py --headless --which best --run_dir <run名> --num_envs 32 --episodes 2

# 2) 从选中的接上
$PY scripts/train.py --headless --resume --load_run <run名> \
    --load_checkpoint model_XXXX.pt --max_iterations 3000 --run_name <run名>_v2
```

可调参数：`--guard-factor`（默认 1e3）、`--guard-patience`（默认 2）。

**把检查点存密一点**能让回滚少丢东西：`pegih_tasks/config/rsl_rl_ppo_cfg.py` 里 `save_interval` 默认 25，
改成 10 的代价是磁盘（每个检查点约 10 MB）。

> 守卫只管 critic 发散。**策略塌陷**（`parse` 掉到 0 但 loss 平稳）是另一回事，它抓不到——
> 实测视觉组在 iter 400 塌过一次又自己恢复了，所以那种情况也不一定需要停。

### 常见报错

| 报错 | 原因 | 处理 |
|---|---|---|
| `Assertion 'normal expects all elements of std >= 0.0' failed` + `CUDA error: device-side assert` | **critic（价值网络）发散到 float32 溢出**，NaN 污染了动作噪声参数。崩溃前 `Mean value_function loss` 会连续几步 ×1e6 级别放大，而 reward / parse / 其它 loss 全部平稳 | **根因未定位**（genpih 也没定位）。实际做法：检查点存密一点，崩了用 `--resume` 从最近检查点接上——**策略本身在崩溃时是好的** |
| `CUDA error: device-side assert` + `Mean value_function loss` 暴涨 | 同上 | 同上；也可试降低学习率或换种子 |
| `out of memory` | 视觉模式 `--num_envs` 太大 | 降到 512 或更低（512 已占 21.7 GB） |
| `Missing key(s): log_std / Unexpected key(s): std` | 检查点是用另一种 `noise_std_type` 存的 | **已处理**：`cnn_policy.load_checkpoint()` 自动迁移，`train.py`/`eval.py` 都走它 |
| 脚本跑完不退出、CPU 一直转 | `simulation_app.close()` 挂起 | `eval.py` 已加守护线程 + 超时 + `os._exit` 兜底 |

> **一处已更正的错误结论**：早期把上面第一条归因于 `noise_std_type="scalar"` 让噪声 `std` 变负，
> 并改成 `"log"`。**这是错的**——改成 `"log"` 后照样崩，只是 `std = exp(log_std)` 里
> `log_std` 变成 NaN，触发**同一条**断言。真根因是 critic 发散。
> `"log"` 保留了（正性由构造保证，本来就更稳），但**它不是修复**。

## 七、改奖励 / 调参的入口

全部在 `pegih_tasks/tasks/peg_hole/peg_hole_env_cfg.py`：

| 想改什么 | 改哪 |
|---|---|
| 初始不对准的偏移量 | `START_OFFSET_XY`（默认 `(0.06, 0.0)`，60 mm） |
| 奖励权重 | `RewardsCfg` 的 `dense`（w=10）/ `parse`（w=1） |
| 回合长度 | `__post_init__` 里的 `episode_length_s`（默认 15 s / 900 步） |
| 动作幅度 | `ACTION_SCALE`（默认 1.5 rad） |
| 相机取景 | `CAMERA_OFFSET_POS` / `CAMERA_OFFSET_ROT`，用 `scripts/cam_offset.py` 重算 |
| 执行器刚度 | `UR10E_PEG_CFG` 的 `ImplicitActuatorCfg` |

**一个已识别的结构性难点**：`dp` 是 peg 尖端到孔原点的三维距离，其中 376 mm 的竖直分量占绝对
主导——横向移动 60 mm 只让 `dp` 从 381 变到 376，所以**密集奖励对"横向移动"几乎没有梯度**，
策略得靠探索自己发现这一步。这大概率就是状态组前 1482 轮卡在平台期的原因。

如果想加速，可以考虑给密集奖励加一项"水平距离"分量（例如按 peg 尖端到孔轴的 xy 距离再加一个
`1/(1+lat/0.043)` 的乘积项）。**但这会偏离 genpih 的设计**，改了之后就不能再和 genpih 的结果
直接对比了——要改请先想清楚这一点。
